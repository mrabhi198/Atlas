=============================================================================== 1.
WHAT IS ATLAS?
===============================================================================

Atlas is an AI-powered software engineering learning ecosystem designed
to help learners become professional software engineers through guided
practice, real-world software engineering missions, AI mentorship, and
production-inspired development workflows.

Atlas is NOT intended to be only: - A LeetCode clone - A HackerRank
clone - A video-course platform - A generic coding playground - A normal
portfolio builder - An AI chatbot that gives code answers

Atlas focuses on engineering thinking rather than only algorithmic
problem solving.

The central idea is:

LEARN -> THINK -> PLAN -> BUILD -> DEBUG -> TEST -> OPTIMIZE -> REFLECT
-> PROVE -> GROW

Atlas teaches learners how software engineering work actually happens.

Instead of presenting hundreds of disconnected questions, Atlas should
progressively expose learners to realistic engineering situations: -
Understand a requirement - Identify constraints - Break a problem into
tasks - Select data structures and architecture - Implement the
feature - Compile and test - Debug failures - Analyze performance -
Improve code quality - Receive guided feedback - Reflect on decisions -
Preserve evidence of the work in the learner’s engineering profile

The product philosophy is: “Learn Like an Engineer. Build Like an
Engineer. Get Hired Like an Engineer.”

===============================================================================
2. WHY ATLAS EXISTS
===============================================================================

Traditional programming education often creates fragmented learning.

A beginner may learn: - Java syntax from one source - Kotlin from
another - DSA from LeetCode - Android from YouTube - Git from
documentation - Projects from tutorials - Interview questions from
another platform

The learner may know individual concepts but still struggle to: -
Understand requirements - Build a complete feature - Debug a real
codebase - Make engineering trade-offs - Structure software - Test
properly - Optimize performance - Explain technical decisions - Build
credible evidence of engineering ability

Atlas is designed to connect those pieces.

Atlas learning should progress from: 1. Fundamentals 2. Logic building
3. Programming concepts 4. DSA/application of logic 5. Framework
concepts 6. Real-world engineering missions 7. Debugging and
optimization 8. Architecture and testing 9. Portfolio evidence 10.
Career readiness

7. THE CORE DIFFERENTIATOR — ENGINEERING MISSIONS
===============================================================================

The Engineering Mission Engine (EME) is the heart of Atlas.

Every learning activity should eventually become an engineering
experience rather than an isolated question.

Mission philosophy: Every mission should answer: 1. Why does this
problem exist? 2. Where would it happen in a real product? 3. Which
engineering concepts are being practiced? 4. How will solving it improve
the learner?

If a mission cannot answer those questions, it should be reconsidered.

MISSION LIFECYCLE

Discover Mission -> Understand Context -> Read Story -> Analyze
Requirements -> Plan Solution -> Code -> Compile -> Run Tests -> AI
Review -> Reflection -> Portfolio Update -> XP / Mastery Update

MISSION HIERARCHY

Career Path -> Track -> Module -> Topic -> Chapter -> Mission -> Stage
-> Task

EXAMPLE

Android -> Jetpack Compose -> State Management -> remember() -> Mission
-> Stage 1 -> Stage 2 -> Stage 3

===============================================================================
9. LOGIC BUILDING
===============================================================================

Atlas should deliberately build logic before expecting advanced
competitive programming performance.

Example progression:

BASIC LOGIC - Variables - Conditions - Loops - Functions - Collections

THEN APPLIED LOGIC - Filtering - Searching - Sorting - Validation -
State transitions - Event handling

THEN ENGINEERING LOGIC - Data modeling - API logic - Caching -
Indexing - Pub/Sub - Authentication - Pagination - Error handling -
Performance optimization

The learner should encounter problems that feel like software features.

Example: Instead of only asking: “Sort an array.”

Atlas may ask: “An Instagram-like application has 50,000 followers.
Implement a follower discovery/search mechanism and compare a linear
scan with an indexed approach.”

This connects DSA to engineering.

===============================================================================
10. GUIDE MODE
===============================================================================

Guide Mode exists to provide structured guidance without immediately
giving the answer.

The mentor should ask questions such as: - What have you tried? - What
do you think the requirement means? - What data do you have? - What
output is expected? - What edge cases exist? - What approach are you
considering? - What would happen if the input became 10x larger?

The system should preserve productive struggle.

Guide Mode should not become: “Here is the complete code.”

The goal is to teach the learner how to think.

===============================================================================
11. SIMPLIFY MODE
===============================================================================

Simplify Mode exists for learners who cannot handle the complete
mission.

Instead of removing the problem, Atlas decomposes it into smaller
stages.

Example:

Original Mission: “Build a follower search system.”

Simplify Mode: Stage 1 -> Understand the data model Stage 2 -> Create
follower list Stage 3 -> Implement linear search Stage 4 -> Measure
performance Stage 5 -> Identify bottleneck Stage 6 -> Introduce indexing
Stage 7 -> Compare approaches Stage 8 -> Reflect

The learner completes one stage before unlocking the next.

Simplify Mode should preserve the underlying learning objective.

===============================================================================
12. HINT SYSTEM
===============================================================================

Atlas uses progressive hints.

Level 1: Requirement clarification

Level 2: Concept explanation

Level 3: Approach suggestion

Level 4: Pseudocode

Level 5: Partial implementation

Level 6: Complete solution

The complete solution should be the final escalation, not the default.

Hint usage can affect: - Learning analytics - Mastery interpretation -
Mission scoring - XP modifiers - Portfolio eligibility, depending on
mission policy

===============================================================================
13. ENGINEERING THINKING CANVAS
===============================================================================

Before the learner writes code, Atlas can guide them through:

STEP 1 — UNDERSTAND - What is the problem? - What inputs exist? - What
outputs are expected? - What constraints exist?

STEP 2 — DESIGN - What data structures are appropriate? - What
architecture fits? - What edge cases exist?

STEP 3 — PLAN - Write pseudocode - Break into subtasks - Estimate time
complexity - Estimate space complexity

STEP 4 — BUILD - Unlock the coding environment

This teaches professional engineering habits instead of immediately
rewarding code typing.

18. SECURE EXECUTION PLATFORM
===============================================================================

The Secure Execution Platform (SEP) is responsible for: - Compilation -
Secure execution - Runtime isolation - Test execution - Performance
benchmarking - Memory measurement - Timeout protection - Resource
isolation - Output collection - Result reporting - Artifact cleanup

HIGH-LEVEL FLOW

Student -> Engineering Mission Engine -> Submission Service -> Queue ->
Sandbox Scheduler -> Secure Sandbox -> Compiler -> Test Runner ->
Performance Analyzer -> Result Generator -> AI Review -> Progress Engine

SANDBOX PRINCIPLES

Every execution should be: - Isolated - Disposable - Stateless -
Ephemeral - Resource-limited - Observable

Preferred architecture direction: Container Runtime -> Firecracker
MicroVM -> Docker Image -> Language Runtime -> Student Code

No sandbox should survive after execution.

33. CURRENT COMPILER / BENCHMARK PROTOTYPE
===============================================================================

The current prototype does NOT represent a production-grade secure
compiler.

It currently uses a Node.js-based benchmark/emulation approach.

The prototype detects whether submitted code appears optimized using
markers such as: - TrieNode - buildIndex - Trie

If an optimized pattern is detected, the prototype returns simulated
performance values.

If a linear implementation is detected, it returns a slower simulated
benchmark.

This is useful for demonstrating the Atlas product concept, but it is
NOT a secure code execution system.

DO NOT describe the current prototype as a production compiler or secure
sandbox.

The production direction is the Secure Execution Platform described
earlier.

48. THE MOST IMPORTANT MENTAL MODEL
===============================================================================

Atlas is not a collection of pages.

It is a connected learning system.

The learner generates data through learning behavior:

Profile -> Learning Path -> Lessons -> Missions -> Attempts -> Hints ->
Compiler Results -> Errors -> AI Guidance -> Reflections -> Mastery ->
Progress -> Engineering Experience -> Passport -> Career Evidence

The Adaptive Learning Engine consumes this information and continuously
improves the next learning experience.

The Mission Engine turns learning into engineering work.

The Secure Execution Platform validates the work.

The AI Mentor helps the learner think.

The Progression System motivates meaningful activity.

The Engineering Passport turns completed work into evidence.

The future Hiring Network connects evidence with opportunities.

This connected loop is the core of Atlas.
